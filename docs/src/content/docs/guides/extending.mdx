## Project structure

After setting up the project, `/config` contains linked files to `custom.css` and `Home.svelte`. This allows you
to easily add your own styles and home page.
For advanced extensions, you can use the designated `custom*` directories.

<FileTree>
	- config
		- Home.svelte Link to /src/components/custom/Home.svelte
		- custom.css Link to /src/custom.css
	- src
		- components
			- custom
				- Home.svelte
				- ... Add your own components
		- locales
			- en.po
			- ... Translation catalogs
		- routes
			- (custom)
				- ... Add your own routes
		- custom.css Add your own styles
	- static
		- custom
			- ... Add your own assets (fonts, images, ...)
</FileTree>

## Custom home page

Enable in config:

```toml
[client.general]
customHome = true
```

When enabled, `/` renders `src/components/custom/Home.svelte`. The map is made available at `/map`.
You can use this to extend Diadem into a full webfront for your mapping project.

Relevant documentation:
- [Svelte](https://svelte.dev/docs)
- [SvelteKit](https://svelte.dev/docs/kit/introduction)
- [Tailwind CSS](https://tailwindcss.com/docs)
- [Bits UI](https://www.bits-ui.com/docs)

## Custom CSS

Global custom styles live in `src/custom.css` (from `config/custom.css`).

It is imported before app styles in `src/app.css`, so you can change theming as you like.

## Add your own custom routes

You can create your own `/about` or `/status` page like this.

<FileTree>
	- src
		- routes
			- (custom)
				- about
					- +page.svelte
				- status
					- +page.svelte
				- ...
</FileTree>

Refer to the [SvelteKit documentation](https://svelte.dev/docs/kit/introduction) to learn more about routing.

## Add your own translations

Diadem uses [Wuchale's Svelte adapter](https://wuchale.dev/adapters/svelte/) for localization.
Write English directly in your components, including interpolation and nested markup:

```svelte
<script lang="ts">
    let { name }: { name: string } = $props();
</script>

<p>Hello <strong>{name}</strong>!</p>
<button title="Open the map">Map</button>
```

There are no translation imports or message keys. In TypeScript utilities, write ordinary strings
and template literals inside functions; the Vanilla adapter extracts those too. Wuchale updates the
catalogs when you run `pnpm i18n:extract`, or start the dev server/build. Both adapters share the PO
catalogs, and the client layout and server locale hook load their compiled catalogs.

The [default extraction rules](https://wuchale.dev/guides/rules/) recognize most user-facing text.
Use `/* @wc-include */` before an abbreviation or lowercase string in script when needed, and
`/* @wc-ignore */` before a technical string. Markup uses HTML comments with the same directives.
Use a descriptive `@wc-context` only when identical English text has different meanings.

Commit the source and `src/locales/*.po` catalogs. Translate `msgstr` entries in those catalogs;
leave `msgid`, `msgctxt`, and numbered placeholders unchanged. Missing translations fall back to English.
Generated loaders and compiled catalogs are ignored by git.

Saved/shared filter titles are a special case: their English templates and parameters are serialized
and localized at display time by `src/lib/features/filters/filterTitle.ts`. The adjacent
`legacyFilterTitles.ts` only reads retired identifiers from older filters. New UI text belongs at
its point of use, not in that compatibility mapping.
